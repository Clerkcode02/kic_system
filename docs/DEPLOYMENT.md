# Deployment

Companion to `CLAUDE.md` and `docs/PROJECT_SETUP.md`. Covers everything needed to take this
repo from a green PR to a running production environment, per SRS §21.

---

## 1. Architecture recap

- **Web**: one Docker image (`docker/Dockerfile`) running nginx + php-fpm, serving the built
  React SPA as static files and proxying `/api`, `/up`, `/health` to Laravel. Stateless —
  autoscale it behind an ALB.
- **Worker**: same image, `docker/entrypoint-worker.sh` (`php artisan horizon`) instead.
  Deployed and scaled independently of web traffic.
- **Scheduler**: same image, `docker/entrypoint-scheduler.sh` (`php artisan schedule:work`).
  Exactly **one** replica — every job in `routes/console.php` is `->onOneServer()`, which
  only protects against overlap, not against two schedulers double-firing at the same
  second.
- **Database**: managed PostgreSQL with the PostGIS extension enabled, matching the version
  pinned in `docker-compose.yml` (`postgis/postgis:16-3.4` → Postgres 16 / PostGIS 3.4).
- **Cache/Queue/Session**: managed Redis, three logical DBs (`REDIS_CACHE_DB`,
  `REDIS_QUEUE_DB`, `REDIS_SESSION_DB`) — never point two of them at the same DB number, or
  a cache eviction can silently drop queued jobs or sessions.
- **Storage**: S3 (or DO Spaces) — one bucket for user content (`AWS_BUCKET`), one separate
  bucket for backups (`AWS_BACKUPS_BUCKET`), so a lifecycle rule written for one can't
  delete the other.
- **Mail**: Gmail API (OAuth2) — never SMTP, never a third-party ESP (CLAUDE.md stack
  table).

## 2. Infrastructure checklist (before the first deploy)

- [ ] **PostgreSQL** — managed instance (RDS/Cloud SQL/etc.), PostGIS extension available
      and enabled (`CREATE EXTENSION IF NOT EXISTS postgis;`), automated backups + **PITR**
      turned on. Confirm your provider actually supports the PostGIS version you developed
      against before committing — not every managed provider does.
- [ ] **Redis** — managed instance (ElastiCache/etc.), sized for cache + queue + session
      traffic combined. Three logical DBs, not three instances — `REDIS_CACHE_DB=0`,
      `REDIS_QUEUE_DB=1`, `REDIS_SESSION_DB=2` by convention (see `.env.example`).
- [ ] **S3 buckets**:
  - User content bucket (`AWS_BUCKET`) — private, presigned-URL access only (CLAUDE.md §9
    mobile-readiness rule 5: presigned direct-to-S3 uploads, never multipart-through-app).
    Lifecycle rule to move old attachments to infrequent-access tier.
  - Backups bucket (`AWS_BACKUPS_BUCKET`) — private, separate from the content bucket.
    Lifecycle rule to expire backups past your retention window (the app-level
    `backup:clean` schedule also prunes per `config/backup.php`'s `cleanup` strategy — the
    bucket lifecycle rule is the second, independent line of defense).
- [ ] **Secrets manager** (AWS Secrets Manager or SSM Parameter Store) holding, at minimum:
  `APP_KEY`, `DB_PASSWORD`, `AWS_SECRET_ACCESS_KEY`, `STRIPE_SECRET`,
  `STRIPE_WEBHOOK_SECRET`, `VAPID_PRIVATE_KEY`, `GEOAPIFY_API_KEY`,
  `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/`GMAIL_REFRESH_TOKEN`, `SENTRY_LARAVEL_DSN`,
  `BACKUP_ARCHIVE_PASSWORD`. None of these belong in a committed `.env` or a plain
  environment variable in the task definition — inject them at container start.
- [ ] **Docker registry** — GHCR by default in `deploy.yml` (uses `GITHUB_TOKEN`, no extra
  setup); swap for ECR/etc. if you're not on GHCR.
- [ ] **ALB / load balancer** — health check path `GET /up` for liveness (fast, no
  dependency checks — see §5), `GET /health` for a deeper readiness signal if your LB
  supports a separate readiness probe.
- [ ] **DNS/TLS** — SPA and API on a shared parent domain (`app.example.com` /
  `api.example.com`) — required for `SANCTUM_STATEFUL_DOMAINS` cookie auth to work at all
  (docs/PROJECT_SETUP.md §5 risk list).
- [ ] **GitHub Environment** named `production` with a required reviewer configured (repo
  Settings → Environments) — this is what makes the `migrate` job in `deploy.yml` actually
  pause for approval. `staging` needs no matching environment/protection rule.

## 3. Environment variables

Full reference lives in `api/.env.example` (local defaults) — this table only calls out
what changes for staging/production and where each value comes from.

| Variable | Local default | Staging/production |
|---|---|---|
| `APP_ENV` | `local` | `staging` / `production` |
| `APP_DEBUG` | `true` | `false` — never `true` in prod, it leaks stack traces |
| `APP_KEY` | generated by `key:generate` | generated once, stored in secrets manager, never regenerated on deploy |
| `DB_HOST`/`DB_PORT`/`DB_PASSWORD` | Docker Compose (`127.0.0.1:5433`) | managed Postgres endpoint; password from secrets manager |
| `REDIS_HOST`/`REDIS_PASSWORD` | Docker Compose, no password | managed Redis endpoint + auth token |
| `SESSION_SECURE_COOKIE` | unset (http) | `true` — TLS terminates at the ALB |
| `SANCTUM_STATEFUL_DOMAINS` | `localhost,localhost:5173,...` | your real SPA domain(s) |
| `FILESYSTEM_DISK` / `AWS_*` | MinIO | real S3 bucket + IAM credentials scoped to that bucket only |
| `AWS_BACKUPS_BUCKET` | unset | the dedicated backups bucket from §2 |
| `MAIL_MAILER` | `smtp` (Mailpit) | `gmail` |
| `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/`GMAIL_REFRESH_TOKEN` | unset | from §6 below |
| `STRIPE_KEY`/`STRIPE_SECRET`/`STRIPE_WEBHOOK_SECRET` | test-mode keys | live-mode keys (or a dedicated staging Stripe account in test mode) |
| `SENTRY_LARAVEL_DSN` | unset (no reporting locally) | your Sentry project's DSN |
| `FEATURE_FREELANCE_MARKETPLACE` | `true` | per-environment — `false` to stage a gradual rollout (SRS §21) |
| `BACKUP_DISKS` | `local` | `backups` |
| `BACKUP_NOTIFICATION_EMAIL` | unset | an on-call-monitored inbox, not a personal address |
| `BACKUP_ARCHIVE_PASSWORD` | unset | set — encrypts the archive at rest |

## 4. First-deploy runbook

1. Confirm every box in §2 is checked and every secret in §3 exists in the secrets manager.
2. Push infrastructure (Postgres, Redis, S3 buckets, ALB, ECS cluster/services or
   equivalent) via your IaC tool of choice — out of scope here, this repo starts from
   "infrastructure exists."
3. Confirm CI is green on the commit you're deploying (`ci.yml` — Pint, Larastan, Pest,
   ESLint, `tsc --noEmit`, Vitest, build, OpenAPI staleness check).
4. Trigger `deploy.yml` (`workflow_dispatch`, environment = `production`), or let it run
   automatically on a push to `main` if you've wired that trigger for your environment.
5. The `build-and-push` job builds `docker/Dockerfile` and pushes to the registry — this
   step needs no approval.
6. The `migrate` job **pauses** for the `production` environment's required reviewer.
   Before approving:
   - Check the migration is additive/reversible (CLAUDE.md §6: "Migrations are additive and
     reversible").
   - For the very first deploy, this is `php artisan migrate --force` against an empty
     database — safe by construction.
7. Approve. `migrate` runs `php artisan migrate --force` as a one-off task using the
   just-pushed image.
8. `deploy-web`, `deploy-worker`, and `deploy-scheduler` roll out in parallel, all pointing
   at the same image tag. ECS's own rolling-update controller
   (`minimumHealthyPercent >= 100`) is what keeps this zero-downtime for the web service —
   nothing extra to configure.
9. Verify:
   ```bash
   curl https://api.yourdomain.com/up       # liveness — 200
   curl https://api.yourdomain.com/health   # readiness — 200, every check "ok"
   ```
   A `degraded` `/health` response with `checks.<name>.status: "error"` tells you exactly
   which dependency (database/redis/storage/stripe/gmail) is unreachable — check that
   service's credentials/network path first.
10. Register the Stripe webhook endpoint (§7) and complete Gmail OAuth2 consent (§6) if this
    is a new environment — both are one-time per environment, not per deploy.

## 5. Health endpoints

- **`GET /up`** — Laravel's built-in liveness probe (`bootstrap/app.php`'s `health: '/up'`).
  Proves the process is running and can render a response. No dependency checks, no auth.
  Use this for the ALB's liveness/health-check path — it must stay fast and side-effect
  free.
- **`GET /health`** — `App\Http\Controllers\HealthController`. Proves every dependency the
  app actually needs is reachable: database, Redis, S3, Stripe, and (staging/production
  only) the Gmail API OAuth2 token. Returns `200` with `{"status":"ok",...}` when every
  check passes, `503` with `{"status":"degraded",...}` otherwise — never a raw 500, and
  never leaks credentials in the error strings. The three outbound checks (S3, Stripe,
  Gmail) are cached for 15s so a load balancer polling this every 1-2s doesn't turn into a
  sustained call volume against three third-party APIs. No auth — an LB health checker has
  no session.

## 6. Gmail API sender authorization (one-time per environment)

Production/staging mail goes out through the Gmail API over OAuth2
(`App\Support\Mail\GmailApiTransport`) — never SMTP, never a third-party ESP.

1. In Google Cloud Console, create (or reuse) a project and enable the **Gmail API**.
2. Create an **OAuth 2.0 Client ID** (Application type: Desktop app is simplest for
   generating a refresh token via the flow below; a Web application type also works if you
   have a redirect URI to catch the code).
3. Configure the OAuth consent screen: add the `https://www.googleapis.com/auth/gmail.send`
   scope, and add the sending account (`GMAIL_SENDER_EMAIL`, e.g. `no-reply@yourdomain.com`
   or a real mailbox you control) as a test user if the app is in "Testing" publish status,
   or publish the app if you want it out of the 100-test-user cap.
4. Run through the OAuth consent flow once, as the sending account, requesting
   `access_type=offline` and `prompt=consent` (required to actually get a refresh token back
   — Google only issues one on the *first* consent unless you force it). Any OAuth2 playground
   or a short one-off script using the client id/secret from step 2 works; you only need to
   do this once per environment since the refresh token doesn't expire under normal use.
5. Store the three resulting values in the secrets manager: `GMAIL_CLIENT_ID`,
   `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`. Set `GMAIL_SENDER_EMAIL` to the account
   from step 3 and `MAIL_MAILER=gmail`.
6. Verify: `GET /health` should report `"gmail": {"status": "ok"}` (this environment check
   only runs when `APP_ENV` is `staging` or `production` — it's skipped locally).
7. If the refresh token is ever revoked (e.g. the sending account's password changed, or
   access was revoked in the Google Account's third-party app list), `/health`'s gmail check
   starts failing with the Google error message verbatim — repeat step 4 to mint a new
   refresh token.

## 7. Stripe webhook endpoint registration (one-time per environment)

1. In the Stripe Dashboard (or a separate Stripe account for staging, in test mode), go to
   **Developers → Webhooks → Add endpoint**.
2. Endpoint URL: `https://api.yourdomain.com/api/v1/webhooks/stripe`
   (`StripeWebhookController`, unauthenticated, signature-verified — CLAUDE.md §7/§14).
3. Select events. At minimum, everything `ProcessStripeWebhookJob` switches on:
   `payment_intent.succeeded`, `payment_intent.payment_failed`, `charge.refunded`,
   `charge.dispute.created`, `transfer.paid`, `transfer.failed`, `account.updated`.
4. Copy the endpoint's **signing secret** into the secrets manager as
   `STRIPE_WEBHOOK_SECRET`.
5. For local dev only, use `stripe listen --forward-to localhost:8000/api/v1/webhooks/stripe`
   instead (docs/PROJECT_SETUP.md) — never point a real Stripe webhook at a dev machine.
6. Stripe Connect also needs `STRIPE_CONNECT_REFRESH_URL` /
   `STRIPE_CONNECT_RETURN_URL` set to real, reachable URLs on your domain (the provider
   onboarding flow redirects there) — apply for Connect access early; platform account
   review and connected-account KYC can take days (docs/PROJECT_SETUP.md §5 risk list).

### Stripe webhook failure alerting

`ProcessStripeWebhookJob` (the queued job that actually processes each event) tags any
uncaught failure with `alert: stripe-webhook-processing-failure` before reporting it to
Sentry (`app/Domain/Payment/Jobs/ProcessStripeWebhookJob.php::failed()`). Set up a Sentry
alert rule filtered on that tag — SRS §21 explicitly calls out that Stripe webhook
processing failures need their own alert, not just "something failed" noise from the
general failed-job stream.

## 8. Observability

- **Laravel Pulse** (`laravel/pulse`) — dashboard at `/pulse`, gated by the `viewPulse` Gate
  (`AppServiceProvider`) to `admin`/`super_admin` roles only.
- **Sentry** (`sentry/sentry-laravel`) — wired via `Sentry\Laravel\Integration::handles()`
  in `bootstrap/app.php`. Set `SENTRY_LARAVEL_DSN` to enable; unset locally (no reporting,
  no noise).
- **Stripe webhook failures** — see §7 above.
- Application logs: `LOG_CHANNEL=stack` writes to stderr in the container (captured by
  whatever your platform ships container logs to — CloudWatch Logs on ECS by default).

## 9. Feature flags

The freelance marketplace (projects, proposals, contracts, milestones) sits behind the
`freelance-marketplace` Pennant flag (`AppServiceProvider::boot()`,
`app/Http/Middleware/EnsureFreelanceMarketplaceEnabled.php`). Controlled by
`FEATURE_FREELANCE_MARKETPLACE` (`config/features.php`) — set to `false` in an environment
that isn't ready to expose it yet. Every gated route 404s while disabled, matching the guest
booking token pattern (CLAUDE.md §5): the API doesn't confirm the existence of a surface a
caller isn't meant to see. Booking/quotation traffic is entirely unaffected — the flag only
gates `v1/projects`, `v1/proposals`, `v1/freelancers/*`, `v1/contracts`, `v1/milestones`, and
freelancer registration.

## 10. Backups and restore testing

`php artisan backup:run` (app code + `pg_dump` of the database, zipped) runs daily at 01:00,
`backup:clean` at 01:30 enforces the retention policy in `config/backup.php`'s `cleanup`
block, and `backup:monitor` at 02:30 fires an email alert
(`UnhealthyBackupWasFoundNotification`, `BACKUP_NOTIFICATION_EMAIL`) if a backup goes stale
or oversized (`routes/console.php`).

This is a **second line of defense**, not the primary recovery path — the managed
Postgres instance's own PITR (§2) is what backs point-in-time restores during normal
operation. Reach for this backup when you need to restore into a *fresh* environment, or
recover from a bucket/account-level disaster PITR can't help with (e.g. the primary
Postgres instance itself is gone).

### Restore testing (run this quarterly, and after any change to `config/backup.php`)

1. Pull the most recent backup archive from the `AWS_BACKUPS_BUCKET` disk:
   ```bash
   php artisan backup:list          # confirm the latest backup exists and its size looks sane
   ```
   Download the corresponding zip from the bucket via the AWS/S3 console or CLI.
2. Unzip it — it contains the `pg_dump` output plus an archive of the application source
   tree present at backup time (per `config/backup.php`'s `source.files.include`).
3. Spin up a scratch Postgres instance (a local `docker compose up postgres` against the
   root `docker-compose.yml` is sufficient — it already has PostGIS):
   ```bash
   docker compose up -d postgres
   createdb -h localhost -p 5433 -U marketplace restore_test
   psql -h localhost -p 5433 -U marketplace -d restore_test -c 'CREATE EXTENSION IF NOT EXISTS postgis;'
   ```
4. Restore the dump:
   ```bash
   psql -h localhost -p 5433 -U marketplace -d restore_test < db-dump.sql
   ```
5. Point a scratch copy of the app at `restore_test` (`DB_DATABASE=restore_test`) and run
   `php artisan migrate:status` — every migration should show `Ran`, with no drift between
   what the dump contains and what the current codebase expects.
6. Spot-check a handful of tables that matter most for recovery correctness: `bookings`,
   `payments`, `audit_logs` row counts roughly match what you'd expect from the backup's
   timestamp.
7. Tear down the scratch database. Record the date and result of this test — if a restore
   test ever fails, that's a production incident in waiting, not a documentation nitpick.

## 11. Rollback procedure

Both database and application rollbacks are gated by the same discipline as forward
deploys: nothing destructive happens without a deliberate, reviewed step.

### Application rollback (no bad migration involved)

1. Identify the last known-good image tag (`ghcr.io/<repo>:<sha>` — every past `main` commit
   that passed CI has one, per `build-and-push` in `deploy.yml`).
2. Re-run `deploy-web` / `deploy-worker` / `deploy-scheduler` (or your platform's
   equivalent `update-service --force-new-deployment` pointed at the old image tag) against
   that tag. No new migration job needed — the schema hasn't changed.
3. Verify `/health` and error rates in Sentry return to baseline.

### Rollback involving a migration

Per CLAUDE.md §6, migrations are additive and reversible — "reversible" here means the
rollback path is **a new forward migration that undoes the change**, not
`php artisan migrate:rollback` against production. `migrate:rollback` is a local/CI dev tool
only; running it against a live database races every currently-connected app server that
still expects the newer schema.

1. Write and review a new migration that reverses the problematic change.
2. Ship it through the normal pipeline: PR → CI green → `deploy.yml` → manual approval on
   the `migrate` job → roll out.
3. If the bad migration already caused incorrect data to be written (not just a schema
   problem), that's a data-repair task on top of the schema fix — handle it explicitly, not
   as a side effect of the rollback migration.
4. In the rare case a migration is actively taking the site down and there's no time to
   write a proper reverse migration, fall back to `php artisan down --render` (SRS §21) to
   take the app offline while you fix it properly, rather than rushing an unreviewed
   rollback into production.

## 12. Local production-image smoke test

Before merging a Dockerfile/entrypoint change, build and boot it against the local Docker
Compose stack:

```bash
docker compose up -d                              # postgres, redis, minio, mailpit
docker build -f docker/Dockerfile -t marketplace-prod:local .
docker run -d --name marketplace-prod-test \
  --network kic-system_default \                  # same network as docker-compose.yml
  --env-file <your local prod-shaped env file> \
  -p 8090:80 \
  marketplace-prod:local
curl http://127.0.0.1:8090/up                      # expect 200
curl http://127.0.0.1:8090/health                   # expect 200, every check "ok"
```

For the worker image, add `--cap-add=SYS_NICE` — Horizon's `payments` supervisor renices
itself (`config/horizon.php`, `nice => -5`) to prioritize payment-queue jobs over lower
tiers, which needs `CAP_SYS_NICE` in the container even when running as root. Grant this
capability on the worker task/service definition in your orchestrator (ECS task definition
`linuxParameters.capabilities.add`, Kubernetes `securityContext.capabilities.add`) — the web
and scheduler entrypoints don't need it.
